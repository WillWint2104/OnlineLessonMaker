# Reusable Geography question and application requirements

Proposed educational designs, not implemented interaction types. Learners should move from clear explanation and explicit modelling to guided practice, independent interpretation and supported argument. The same question family can use maps, infographics, tables, photographs or text evidence across both courses. Every new lesson needs authored questions, checked model responses and progressively withdrawn scaffolds; an interactive visual alone is not a lesson.

For each approved authored question record its purpose, source IDs and revisions, expected response/criteria, misconceptions, worked/model response, scaffold level, answer-release conditions and accessibility/no-device equivalent. Keep authored givens and model content separate from learner response/view state. Do not add new shared schema fields in this planning task.

## Three principal application families to investigate

1. **Map explorer:** bounded question-owned maps/thematic layers, with optional migration-flow or spatial-change adapters (C04/C07/C08). Test its educational benefit across actual tasks against static alternatives. It is not a full GIS editor.
2. **Statistics workbench:** linked graphs/tables, metadata/units, comparisons, population pyramids and approved construction exercises (C05/C06 and relevant C09 scope). Reuse existing charts where appropriate; avoid a new general data framework before proving the need.
3. **Geographic source investigation:** existing source inspection/provenance plus coherent source-question/response workflows (C03 with C01/C02/C10). Preserve the single-source viewer contract; propose any extra comparison/annotation scope separately.

These are reusable capability groupings for comparison, not approved architecture, vendors or three applications to build automatically. The host question/response system remains common. Minimum viable scope follows the whole coverage matrix and pilot review; high-value interactions may become essential after that review even where a static teaching fallback exists.

The separate JSON-informed classroom consumer is a design proposal only (C11). Its projector, note-taking, controlled reveal, print, relief and no-device needs must reuse content/completed widget sources through isolated adapters; they cannot add presenter behaviour to the online learner player.
